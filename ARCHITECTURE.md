# Архитектура агента огневых работ

## Основания и ограничения

`REQUIREMENTS.md` — неизменённое исходное задание. `BUSINESS_RULES.md` фиксирует согласованные уточнения, статусы, допущения и нерешённые вопросы; исходный регламент и инженерные допущения не смешиваются. Это проектное описание, реализация и метрики пока отсутствуют.

Выбрана гибридная схема: одна LLM извлекает факты из свободного текста, детерминированный Python проверяет правила. Это позволяет тестировать границы, приоритет и формирование ответа без LLM и сохранять основания решений. Риск неверного извлечения остаётся, поэтому недопустимо представлять проверку схемы как проверку истинности фактов. Для прототипа достаточно одного процесса и файлов; очередь, БД, второй проверяющий агент и универсальный движок правил не нужны.

Стек: Python 3 и небольшой набор зависимостей для HTTP и валидации схем; точные версии фиксируются при реализации. Стартовая модель для нашего прогона — `gpt-5-mini` при наличии доступа; имя модели и сервер не зашиваются в код. API OpenAI-совместимый, модель проверяющего может отличаться. Поддержка строгого режима JSON Schema у совместимых серверов не предполагается: локальная валидация обязательна всегда.

## План структуры

```text
README.md  REQUIREMENTS.md  ARCHITECTURE.md  BUSINESS_RULES.md
results.json  eval_report.md  Dockerfile  run_tests.sh
app/          # CLI, клиент LLM, схемы, правила, журнал и промпт
tests/        # автономные тесты кода
eval/         # исходные заявки, эталоны, дополнительные кейсы и прогон
```

Структура ориентировочная: не требуется создавать отдельный файл или класс для каждой операции. README документирует локальный запуск одной командой на чистой машине, Docker, настройки, результаты измерений, ограничения и масштабирование.

## Ответственность и данные

Вход — JSON-массив объектов `{"id": ..., "text": "..."}`. Идентификатор сохраняется без подмены; каждый результат связывается с соответствующим входом. Проверка входа различает ошибку формата всего файла и пустой/слишком длинный текст отдельной заявки. Для повреждённого файла или невозможности корректно связать результат с входом процесс сообщает ошибку и завершает работу с ненулевым кодом; не создаёт фиктивный успешный результат.

LLM получает инструкции на извлечение фактов и недоверенный текст. Промежуточная схема содержит номер наряда, сведения и дату инструктажа, близость складов угля и ГСМ, письменное согласование, огнетушитель, наблюдающего и его роль, тип места, ветер и его источник, высоту и отдельный допуск. Для каждого существенного факта предусмотрены значение, состояние (известно, неизвестно, противоречиво) и подтверждающий фрагмент текста при наличии. Для отрицаний, приблизительных величин и интервалов сохраняется достаточно информации для проверки порогов; отсутствие значения не превращается в `false`. Точные типы и формат определяются реализацией и тестируются схемой.

Python валидирует ответ, проверяет факты и независимо вычисляет статусы правил и итог по `BUSINESS_RULES.md`. Выход для каждой заявки имеет поля `id`, `decision`, `rules`, `explanation`, `missing`: решение — одно из трёх русскоязычных значений задания, `rules` — номера применимых оснований, `explanation` — краткое объяснение, `missing` — список недостающих данных. При отказе сохраняются также известные пробелы. Выход валидируется перед записью.

## Поток и отказы

1. Прочитать и проверить пакет; для каждого допустимого `id` проверить текст и ограничение длины. Пустой и чрезмерно длинный текст ведут к эскалации без вызова LLM, без незаметного обрезания.
2. Передать заявку в LLM как данные и получить структурированные факты. Тайм-аут и число повторов ограничены; предел длины и настройки явно документируются.
3. Локально проверить JSON, типы, обязательные поля и согласованность. При невалидном ответе или недоступности после ограниченных повторов — эскалация с технической причиной.
4. Проверить П1–П6, агрегировать по П7 и согласованному приоритету, сформировать и проверить результат.
5. Записать журнал и пакетный выход. Ошибка журнала явно сообщает о сбое и приводит к ненулевому коду процесса; успешный допуск без обязательной записи не объявляется.

Промпт запрещает выполнять инструкции в заявке и ограничивает задачу извлечением; заявка отделяется от системных инструкций. LLM не выдаёт авторитетное решение. Проверка схемы, детерминированные правила и инъекционные eval-кейсы уменьшают риск, но не гарантируют защиту от искажения фактов моделью.

## Журнал

В `/data/journal/` сохраняется отдельная структурированная запись на каждую обработку с уникальным именем, без перезаписи предыдущих запусков: вход, время, модель и версия промпта, сырой ответ модели или сведения о сбое, проверенные факты, результаты пунктов, итог и объяснение, недостающие данные. При повторах сохраняются ответы или ошибки попыток, достаточные для разбора. Секреты и ключ API в журнал не записываются. Если журнал записать невозможно, процесс сообщает ошибку и завершается ненулевым кодом.

## Тесты и качество

Автономные тесты без LLM проверяют даты, пороги 10 м, 10 м/с и 1,8 м, применимость, неопределённость, приоритеты, разбор и валидацию ответов, ошибки и инъекционные данные через подставной клиент. Eval с реальной моделью содержит неизменённые эталоны 1–8 и минимум десять дополнительных случаев с ожидаемыми результатами; печатает расхождения и сохраняет отчёт. Документированные противоречия эталонам остаются расхождениями, а не скрываются из метрики. Заявки 9–11 обрабатываются для `results.json`, но ответы заказчика для них не выдумываются. Измеряются время и стоимость по фактическому использованию токенов и тарифу, указываются модель, ограничения и условия прогона. Без реального вызова показатели не заявляются.

## Контракт и расширение

`docker build .` создаёт образ; `docker run -v <папка>:/data --env-file <файл> <образ>` читает `/data/input.json`, пишет `/data/output.json` в формате `results.json` и журнал в `/data/journal/`. Подключение только через `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. `run_tests.sh` запускает тесты внутри контейнера и возвращает 0 при успехе; способ вызова документируется в README. В корне при сдаче обязательны также `results.json` и `eval_report.md`.

Для нового правила: добавить нужные факты в схему и описание извлечения, реализовать небольшую функцию с общим форматом результата, подключить её к агрегатору, добавить тесты и eval. Если факты уже есть, схема и промпт не меняются. При 500 заявках за смену сначала измерить задержку, стоимость, лимиты API и ошибки журнала; затем по необходимости добавить ограниченную параллельность и устойчивую очередь.
